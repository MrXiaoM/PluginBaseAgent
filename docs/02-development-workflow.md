# 插件开发工作流

本工作流适用于新功能、缺陷修复、兼容性调整、构建维护和代码审查。它将 `01-agent-contract.md` 的强制规则落实为可执行阶段。

## 阶段 1：建立任务边界

开始时记录：

- 需求目标、可观察行为与非目标；
- Minecraft 目标版本和最低兼容版本；用户明确给出的版本号原样文本，以及必要时按 `server-api/minecraft-version-integrity.md` 进行的 Wiki 核验结果；
- API 选择：默认 Spigot，或用户明确选择 Paper；
- 是否涉及 NMS、可选依赖插件、嵌入式外部依赖、数据库、文件迁移、网络/动态库、Folia 或箱子容器菜单；
- 若涉及 `ItemPacketModifier`：项目锁定的 Maven Central GAV、`PacketEvents` 接入边界、包回调线程、客户端回传还原、重载/停用释放与真实物品数据边界；
- 若涉及 `EvalEx-j8`：项目锁定的 Maven Central GAV、公式键契约、变量白名单、结果范围、精度/舍入、缓存替换与异步失效边界；
- 若涉及箱子容器菜单：选择硬编码或配置驱动模式、所需 `gui`/`actions`/`l10n`/`paper` 模块、顶部 slot 与玩家背包交互策略、重载/关闭/异步回调边界；
- 预计修改的项目文件和资源；
- 可用于验证的构建任务、测试环境和服务器版本。

阅读当前项目的 `build.gradle.kts`、`plugin.yml`、主类和相邻功能模块。不要以模板文档覆盖现有项目已验证的特殊约定；发现差异后先判断它是合理的项目定制还是遗留缺陷。

## 阶段 2：选择实现层

按下列优先级决定实现位置：

1. 目标 Spigot API 已提供、且符合目标版本与兼容性要求的稳定能力；
2. `PluginBase` 已提供的跨版本或跨服务端抽象；
3. 已明确选择 Paper 后的 Paper 能力，并隔离为适配层；
4. 用户明确允许且完成版本资料核验后的 NMS/CraftBukkit 实现；
5. 无法满足时，向用户说明边界，而不是构造未验证接口。

涉及框架能力时，先确定需要哪个 `PluginBase` 模块。不要仅因类名“像是可用”就添加依赖或调用成员。

涉及箱子容器菜单时，先以项目实际解析的 `gui` 构件查询计划调用的 `IGuiHolder`、`GuiManager`、`AbstractGuiModule`、`AbstractGuisModule` 或 `LoadedIcon`。配置点击动作或语言消息时，再确认实际已启用的 `actions`、`l10n` 构件。框架源码只确认能力边界；设计还必须读取目标项目已有的菜单类、YAML 和加载器，不能把模块源码误当完整菜单示例。

涉及 `ItemPacketModifier` 或 `EvalEx-j8` 时，先阅读 `external-libraries/README.md` 与对应专题文档，再按项目锁定的 Maven Central 构件查询 POM、sources/Javadoc。前者只能用于客户端虚拟展示，必须设计发回物品还原与监听器释放；后者只能作为受约束的表达式求值器，必须先定义变量、结果、精度与业务校验，不能把公式文本当可信业务逻辑。

## 阶段 3：取得并记录证据

对每个会影响实现的版本敏感结论，按 `evidence/dependency-index-zoo-tool.md` 或 `evidence/dependency-index-cli.md` 查询目标版本资料。陌生 Gradle 依赖先通过真实模块依赖、类、运行字节码签名和继承关系缩小范围；已知接收者类型时沿其 `extends`/`implements` 链查找成员实际声明处。索引定位后，通过 `show --verbose` 取得主 JAR 与资料路径：优先直接读取同版本 `sources.jar` 的目标条目，缺少 sources 才临时 Vineflower 反编译主 JAR。完整步骤见 `evidence/query-playbook.md`；不要解包到 `state/`，也不要以反编译覆盖字节码签名。将可复用的已验证边界精简写入 `state/notes/`。

最低记录内容：

```markdown
- 结论：<采用的接口或框架行为>
- 目标：<Spigot 或 Paper>，<精确 Minecraft/API 版本>
- 来源：<运行字节码、sources、Javadoc、Gradle 元数据或临时 Vineflower 反编译>
- 位置：<GAV、SHA-256、归档内路径、类名、成员签名或 Javadoc 锚点>
- 适用性：<为何满足需求；是否有弃用、实验性、线程或版本边界>
- 回退：<不适用或无法支持的版本处理方式>
```

如资料不足，终止当前设计分支。可改为使用较低层的已证实接口、缩小兼容范围、等待资料同步，或向用户确认替代方案。

## 阶段 4：设计与分层

按职责组织代码，而不是把所有功能堆进主类：

- 主类：Options、框架扩展点、少量项目级注册和编排；
- `func/`：项目级模块、管理器和框架适配基类；
- `commands/`：命令执行、补全与权限分发；
- `config/`：配置映射、语言键和配置数据；
- `data/`：领域数据和序列化对象；
- `manager/`：生命周期明确的状态管理；
- `event/`：对外事件定义；
- `depend/`：可选外部插件的检测和适配；
- `api/`：对其它插件公开且稳定维护的接口。

新增自动注册类前，核对其父类、`@AutoRegister`、构造器类型和初始化时机。新增配置文件前，明确默认资源、首次保存、重载行为和向后兼容策略。新增箱子容器菜单时，明确每玩家实例与共享模型的边界、顶部 Holder、slot 路由、点击/拖拽/关闭、父子菜单、刷新频率、点击锁和异步结果失效条件。

## 阶段 5：实施

实施时遵守以下顺序：

1. 先更新构建依赖、嵌入式外部库的范围/重定位和 `PluginBase` 模块选择；
2. 再更新 `plugin.yml`、配置默认资源和语言资源；
3. 创建领域模型、适配层和模块；
4. 最后在合适的框架生命周期中进行注册、加载和清理；
5. 不把可选依赖类加载风险扩散到主路径；使用已验证的存在性检测和隔离边界；
6. 通过框架调度器处理延迟、异步或周期任务；不假设所有服务端都允许相同的主线程访问方式。

使用最小改动解决需求。不要借功能任务无关重写构建脚本、迁移依赖版本或替换框架抽象。

## 阶段 6：静态复核

逐项检查：

- 导入和调用均属于已选 API 与目标版本；
- Paper 调用没有泄漏到 Spigot 默认路径；
- NMS 调用符合已确认许可和映射；
- 所需 `PluginBase` 模块已加入，未引入无关模块；
- `OptionsBuilder` 的选项与实际功能一致；
- 自动注册、配置保存/重载和可选依赖失败路径完整；
- `ItemPacketModifier` 的客户端展示与真实物品数据隔离、虚拟 Lore 幂等标记、客户端回传还原、包监听器停用释放和高频回调边界完整；
- `EvalEx-j8` 的公式变量白名单、类型/范围/精度校验、解析失败回退、缓存/副本并发和业务副作用前校验完整；
- 箱子容器菜单的顶部 Holder、玩家背包/拖拽取消策略、重复点击、关闭/退出、重载和异步回调边界完整；
- `plugin.yml` 与主类、命令和依赖声明一致；
- Shadow 规则覆盖 `PluginBase` 与会打进 JAR 的实现依赖。

## 阶段 7：构建与产物验证

优先运行项目自带的 Gradle Wrapper。至少执行能编译和产出 Shadow JAR 的任务；实际任务名以项目配置为准。

成功编译后不立即宣称完成。继续检查：

1. 是否产出目标插件 JAR；
2. JAR 中是否包含重定位后的 `PluginBase`；
3. JAR 中是否保留 `META-INF/PluginBaseHolders`；
4. 是否误将服务器 API、开发资料或未重定位实现依赖打进 JAR；特别检查 `ItemPacketModifier`、`EvalEx-j8` 及其已确认需要嵌入的传递依赖；
5. `plugin.yml` 是否位于 JAR 根目录且可被服务端读取；
6. 有服务器环境时，是否在目标版本上启用、注册命令和执行关键路径。

若运行环境不可用，明确写“未进行服务端启动验证”，并列出已完成的构建与归档检查。

## 阶段 8：交付说明

交付内容至少包含：

- 修改的文件和各自原因；
- API 选择、Minecraft 版本与 PluginBase 模块；
- 关键接口/框架结论的证据；
- 已执行命令和结果；
- 未执行的验证、兼容性边界和已知风险。

不要把“看起来合理”“理论上兼容”或“未运行”表述为已验证结论。
