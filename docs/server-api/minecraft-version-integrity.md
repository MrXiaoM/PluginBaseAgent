# Minecraft 版本号完整性约束

用户明确提供的 Minecraft 版本号是**不可擅自更正的输入事实**。Agent 必须逐字保留、传递和查询该版本号；无论它是否符合 Agent 已知的历史版本模式、是否比知识库更新、是否不符合传统 `1.x.y` 形式，都不得改写、截断、归一化或宣称其是拼写错误。

本约束优先于 Agent 的记忆、训练数据、旧文档、旧示例、IDE 提示和任何“看起来更常见”的版本格式。

## 强制规则

当用户指定 Minecraft 版本 `V` 时：

1. 将 `V` 原样记录为目标 Minecraft 版本；
2. 在需求说明、证据记录、工具参数、资料目录和交付说明中保留 `V` 的原始文本；
3. 使用 `V` 查询 Spigot/Paper 元数据、构件、sources 和 Javadoc；
4. 若资料未找到，报告“尚未为用户指定版本 `V` 取得资料”，而不是尝试改用另一版本；
5. 只有用户明确更改版本，或目标项目现有构建文件明确指定了不同版本且需要用户确认冲突时，才能采用不同版本；
6. 不得把未能查询到资料解释为版本不存在、拼写错误或可以自动回退。

## 禁止行为

以下行为均被禁止：

- 将 `1.21.11` 擅自改为 `1.21.1`、`1.21` 或其它“更常见”的形式；
- 将 `26.1`、`26.2` 等前沿命名方式改写为虚构的 `1.26.1`、`1.26.2` 或其它旧式编号；
- 去掉、增加或重排版本号段；
- 因训练数据停留在旧版本而否定用户给出的版本；
- 因 Maven 坐标未命中就静默选择最接近的已知版本；
- 在构建脚本、`plugin.yml`、证据记录或发布说明中写入被擅自变更的版本；
- 使用“可能是笔误”“应该是”“通常写作”之类措辞把猜测包装成事实。

## 资料查询与构件解析

Minecraft 版本文本与 Maven 构件版本不是同一概念，但它们的映射也必须以用户输入为起点。

对用户给出的版本 `V`：

1. 先从目标项目的 `build.gradle.kts` 读取已经声明的 API 构件版本；
2. 若项目尚未声明，使用 `V` 原样向注册表配置的仓库查询元数据；
3. 记录得到的精确 API 坐标、元数据时间、sources/Javadoc 归档和 `SHA-256`；
4. 若仓库命名规则与 `V` 不同，只能根据仓库元数据建立映射并记录证据；
5. 若无法建立映射，停止版本敏感实现，报告需要的资料或用户确认；不得凭近似版本猜测坐标。

例如，用户指定 `1.21.11` 时，查询目标必须仍是围绕 `1.21.11` 的构件/元数据，而不是自动降为 `1.21.1`。用户指定 `26.1` 或 `26.2` 时，必须按原命名方式查询；不得补造 `1.` 前缀。

## 版本存在性疑问时的 Wiki 核验

当 Agent 对用户给出的 Minecraft 版本是否存在、其命名是否前沿或是否不符合旧版模式存在疑问时，可访问中文 Minecraft Wiki 的**原样版本号**页面确认：

```text
https://zh.minecraft.wiki/w/Java版<版本号>
```

其中 `<版本号>` 必须逐字替换为用户提供的文本，不做任何改写。例如用户指定 `26.2` 时，应查询：

```text
https://zh.minecraft.wiki/w/Java版26.2
```

使用规则：

1. Wiki 核验是为了消除 Agent 对用户版本输入的疑问，不是获得擅自修改版本的许可；
2. 即使 Wiki 页面无法访问、页面不存在或检索失败，用户指定版本仍保持原样；正确结论是“尚未完成 Wiki 核验”，而不是“版本不存在”或“可自动改为相近版本”；
3. Wiki 可证明版本名称与发布信息，不能替代目标 Spigot/Paper API 的 Maven 元数据、sources/Javadoc，也不能证明某个接口存在；
4. 完成核验后，在证据记录中写明访问的原样 URL、访问时间和结果摘要；
5. 后续 API 构件查询仍以用户原样版本为起点，按仓库元数据建立映射。

## 与项目现有版本冲突

若用户版本 `V` 与项目 `build.gradle.kts`、`plugin.yml`、测试服务端或现有文档中的版本不同：

- 如任务明确要求迁移到 `V`，将其视为迁移目标并按升级流程处理；
- 如无法判断用户描述的是目标版本、当前版本还是最低兼容版本，提出最少必要的澄清问题；
- 在澄清前不得静默保留旧版本，也不得静默把 `V` 改为旧版本；
- 交付说明必须区分用户指定版本、构建 API 版本、最低兼容版本和已启动验证版本。

## 证据记录要求

涉及版本的每条证据记录都应包含：

```markdown
- 用户指定 Minecraft 版本：`<原样文本>`
- API 构件：`<group>:<artifact>:<精确版本>`
- 映射依据：`<构建脚本、仓库元数据或用户明确说明>`
- 验证状态：`<已同步资料 / 未取得资料 / 已启动验证>`
```

该格式使后续 Agent 能分辨“用户输入”“构件坐标”和“已验证范围”，不会用其中任一项擅自替代另一项。

## 失败时的正确表达

正确：

```text
用户指定的目标 Minecraft 版本为 `26.8`。当前尚未取得与该版本对应的 API 构件资料，因此不能验证计划调用的接口；未改用其它版本。
```

错误：

```text
`26.8` 看起来像笔误，已按 `1.26.8` 实现。
```

版本完整性是取证流程的前提；没有保留正确输入，再完整的源码/Javadoc 查询也不能证明代码针对用户所需版本正确。
