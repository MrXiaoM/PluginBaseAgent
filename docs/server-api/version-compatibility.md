# 版本兼容与升级

Minecraft 服务端 API 的版本字符串相近，不代表类、成员、事件语义、线程约束或服务端实现保持不变。兼容性必须以项目承诺的最低版本、精确 API 构件与实际启动验证共同证明。用户明确给出的 Minecraft 版本号必须原样保留；陌生、前沿或非传统命名不能被擅自改写，详见 `minecraft-version-integrity.md`。

## 版本基线

每个插件项目应明确维护：

| 项目 | 必须记录的值 |
| --- | --- |
| 编译 API | Spigot 或 Paper、精确构件版本 |
| 最低运行版本 | 最低 Minecraft/服务端版本 |
| 已验证版本 | 实际构建与启动测试过的版本集合 |
| Java 目标 | `targetJavaVersion` 与实际服务端 Java 要求 |
| PluginBase | 版本、已选模块、资料哈希或来源 |
| 可选依赖 | 名称、支持版本、缺失时行为 |
| 不支持边界 | NMS、Paper-only、特定实现或旧版本限制 |

不要将 `plugin.yml` 的 `api-version` 单独视为完整兼容声明；它不能替代依赖、字节码、运行时行为和资料验证。

## 升级流程

升级 Minecraft、Spigot、Paper、PluginBase、Gradle 或主要依赖时：

1. 固定升级前的构建脚本、依赖锁定信息和已知验证结果，并原样记录用户指定的迁移目标版本；
2. 对陌生版本按 `minecraft-version-integrity.md` 原样核验版本命名，再同步升级前后精确版本的 sources/Javadoc/元数据；
3. 列出所有受影响导入、成员、事件、枚举、反射字符串、配置名和生成资源；
4. 比较符号是否存在、签名是否变化、是否新增弃用/实验性/线程说明；
5. 更新构建脚本、仓库、PluginBase 模块和动态库解析信息；
6. 更新配置迁移、Material/枚举兼容和可选依赖适配；
7. 构建并检查 Shadow 产物；
8. 在每个声明支持的目标服务端启动并执行关键路径；
9. 更新已验证版本和未验证边界。

未来的资料工具会协助比较基本符号差异，但不会自动证明复杂运行时语义、NMS 映射、服务加载器或线程安全。

## 最低版本优先

若项目承诺兼容多个版本，所有公共主路径必须能在最低版本资料中得到证明。高版本增强应满足以下之一：

- 通过 PluginBase 或项目兼容层已被安全抽象；
- 隔离到高版本可选实现，并有真实的低版本回退；
- 通过用户明确允许提高最低版本。

不得只在最新 API 上实现，再用 `try/catch` 声称向下兼容。类验证和静态引用可能早于异常捕获发生。

## Snapshot 注意事项

`spigot-api`、`paper-api` 等 Snapshot 可能在相同版本字符串下更新内容。每次资料同步记录：

- 构件坐标和仓库 URL；
- 下载或缓存来源；
- 获取时间；
- `SHA-256`；
- sources/Javadoc 是否齐全；
- 索引工具版本。

同坐标哈希变化时，旧查询结论必须标记为需复核；不要把它当成不变发布版本。

## 兼容性声明格式

发布说明或项目文档应使用事实化表达：

```text
编译基线：Spigot API 1.20-R0.1-SNAPSHOT。
已启动验证：Spigot <精确版本>、Paper <精确版本>。
最低支持：<版本>，依据为 <资料与测试范围>。
未验证/不支持：<版本或能力>。
```

没有启动测试时，应写“已完成编译/归档检查，未完成目标服务端启动验证”。
