# NMS、CraftBukkit 与反射边界

NMS、CraftBukkit、内部实现类、服务端版本包和反射不是常规 API 的替代品。除非用户明确允许并确认版本策略，否则按禁止使用处理。

## 使用前提

只有同时满足以下条件才可设计内部实现方案：

1. 用户明确同意使用 NMS/CraftBukkit/反射；
2. Spigot/Paper/PluginBase 的公开 API 已查询且确实无法满足需求；
3. 精确 Minecraft、服务端实现、映射命名空间和构建工具已锁定；
4. 目标版本的源码、映射或权威资料可本地查询；
5. 已决定每个支持版本的实现、测试和故障处理；
6. 内部代码能隔离在小范围适配层，业务层不依赖其类型。

## 禁止的替代行为

- 不能通过猜测 `net.minecraft.server.vX_Y_RZ` 包名解决资料缺失；
- 不能以反射字符串掩盖未知方法或字段；
- 不能将“编译能找到 Spigot 服务端 JAR”当作跨版本支持；
- 不能把内部类暴露到项目公共 API、主类或自动注册主路径；
- 不能在未验证映射/运行环境下生成 NMS 代码占位实现。

## 设计方式

内部实现应置于类似 `compat/nms/<版本>/` 的私有层，并通过不含 NMS 类型的项目接口暴露能力。每个适配器必须记录：

- 支持的服务端与 Minecraft 精确版本；
- 映射名称空间与构建配置；
- 使用的内部类、方法、字段及资料证据；
- 初始化验证和失败时行为；
- 回退或明确禁用策略；
- 启动测试结果。

NMS 变更与普通 API 升级分开提交和审查，防止范围扩大。

## 反射

反射只能用于已验证的可选能力或兼容分支，且需：

- 查证目标类、构造器、方法、字段和访问条件；
- 将反射封装在单个适配器；
- 验证结果并保留清楚、可诊断的错误；
- 不在静态初始化阶段执行高风险反射；
- 不以吞掉异常继续返回伪造的“成功”状态。

反射减少的是编译时直接链接，不减少版本证明、运行时测试和维护责任。
