# 代码与项目风格

本项目风格来自模板项目和现有 PluginBase 插件的共同结构。风格服务于可维护性、生命周期清晰度和跨版本兼容；它不替代目标项目已经稳定的局部约定。修改既有代码时，优先与附近已验证代码一致。

## 包与职责划分

| 包 | 放置内容 |
| --- | --- |
| 根包 | 主类、构建常量相关入口、少量项目级公开入口 |
| `func/` | PluginBase 模块、功能管理器、项目框架适配基类 |
| `commands/` | 命令执行、补全与权限分发 |
| `config/` | 配置映射、语言/消息 Holder、配置加载逻辑 |
| `config/data/` | 配置中使用的结构化值对象 |
| `data/` | 领域数据、序列化数据、玩家/持久化数据模型 |
| `manager/` | 有清晰生命周期的领域管理器 |
| `api/` | 对其它插件或项目模块承诺维护的公开接口 |
| `event/` | 项目自定义事件 |
| `depend/` | 外部插件检测、版本分支和适配器 |
| `gui/` | 业务 GUI、Holder 与交互逻辑 |
| `utils/` | 无状态、通用且与具体领域低耦合的辅助代码 |

不要以 `utils/` 作为未经设计的业务逻辑堆放区，也不要让主类成为所有功能的容器。

## 类与接口

- 类名、方法名、字段名使用清晰、稳定的英文技术命名；资源面向用户的文本放入语言/配置资源。
- 接口以 `I` 前缀仅在项目/框架现有约定已使用时保持一致；新公开 API 需先考虑是否真的需要跨模块承诺。
- 枚举用于封闭且稳定的值域；Minecraft API 名称或可变配置值不应因便利而硬编码成无法迁移的枚举假设。
- 可选依赖适配类放到 `depend/` 或明确兼容层，不使核心业务类直接依赖其类型。
- 多态适配优先通过明确接口/提供器注册，而不是遍布业务层的 `instanceof` 和类名字符串判断。

## 空值、异常与日志

- 使用当前项目已有的 `@NotNull`、`@Nullable` 约定，让边界可读；不要用无意义注解掩盖未验证输入。
- 外部输入、配置、网络、数据库和可选依赖必须验证；错误信息至少包含对象、键、路径或依赖名称。
- 不吞掉会影响正确性的异常。只有确实允许的兼容探测失败可捕获，并记录最小必要上下文和可预期回退。
- 使用插件/模块日志接口输出运行期信息；避免在高频路径日志刷屏。
- 对用户可见错误提供可执行提示；对开发诊断保留足够上下文，但不泄露密码、连接字符串或敏感数据。

## 物品图标与自定义数据

- 创建或编辑硬编码 `ItemStack` 图标时，优先使用 `AdventureItemStack`；它通过 PluginBase 的 `ItemEditor` 统一处理 Adventure `Component`、MiniMessage 名称和 Lore。
- 未使用 Adventure 的既有代码路径，以及发光、自定义模型数据、物品模型等辅助操作，使用 `ItemStackUtil` 的已验证方法。不要在各业务类散落重复的 `ItemMeta` 获取、修改、写回代码。
- `AdventureItemStack`、`ItemStackUtil` 的具体重载与版本能力必须在项目锁定的 PluginBase 资料中查询，不能按记忆假定签名。

## 物品自定义数据

- 当构建脚本已引入 `item-nbt-api` 时，物品自定义数据必须通过该依赖读写；不得为同一用途使用 `PersistentDataContainer`、`PersistentDataType` 或 `ItemMeta#getPersistentDataContainer()`。
- 这是性能与维护性约束：PDC 不应作为安装 `item-nbt-api` 后的物品数据回退方案。新增或迁移物品标记、标识符、数值、序列化数据时，先查询当前 `item-nbt-api` 版本资料，并将访问封装在项目的物品数据适配层。
- 非物品对象的 PDC 用途不属于本条规则；审查时必须按实际接收对象确认，不能因出现同名 API 就把实体、方块或其它容器的数据访问误判为物品数据。

## 配置与资源

- 配置键和资源文件名视为公开契约；改名时准备迁移或兼容读取。
- 默认值、类型、范围和缺失行为应在资源注释或配置映射中清楚表达。
- 配置中的 Bukkit 枚举/注册表类型统一通过 `Util.valueOr(...)`、`Util.valueOrNull(...)` 或 `Util.parseMaterial(...)` 等包装方法解析；不使用 `Enum.valueOf(...)`、`Material.valueOf(...)`。
- 语言消息使用已有语言模块/Holder 约定，避免在业务类散落硬编码面向用户文本。
- 新增 `plugin.yml` 命令、依赖或软依赖时同步更新代码、权限和发布说明。

## 生命周期与资源管理

- 在主类扩展点做项目级编排，在 Holder 模块做功能注册和清理。
- 延迟/周期任务保存句柄并设计重载、停用时的失效策略。
- 数据库、文件、网络和缓存资源有明确创建、替换与关闭责任。
- 静态状态仅用于框架/项目已验证的访问入口；不以静态可变集合逃避生命周期管理。

## 兼容代码

- 将版本判断、Paper/NMS 代码和反射封装在小范围适配器。
- 每个兼容分支记录目标版本、证据与失败行为。
- 优先使用 PluginBase 的 `ItemEditor`、`InventoryFactory`、`getScheduler()` 等抽象。
- 不把宽泛 `try/catch` 当作跨版本方案；可加载不代表语义正确。

## 改动原则

- 先理解现有结构和调用者，再修改公共 API、配置格式或生命周期。
- 最小化无关格式化、重命名和依赖升级，方便审查与回滚。
- 新增功能同时补齐资源、权限、依赖声明、重载/停用策略和验证。
- 每个版本敏感改动附带证据记录和已执行检查。
