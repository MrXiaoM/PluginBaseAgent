# 配置、数据库与动态库

PluginBase 将主配置、数据库、可选动态库与项目生命周期关联起来。每项能力都需在主类 Options、构建依赖、资源文件和运行期逻辑之间保持一致；只改其中一处通常会造成启动或重载失败。

## 主配置与重载

默认情况下，`BukkitPlugin.reloadConfig()` 管理插件数据目录下的 `config.yml`：

1. 缺失时从 JAR 资源保存默认 `config.yml`；
2. 加载配置；
3. 若启用 `enableConfigGotoFlag`，按框架规则解析 `goto`；
4. 调用主类 `beforeReloadConfig(...)`；
5. 若启用数据库，重载数据库配置并按 Options 决定是否重连；
6. 通知已注册 Holder 执行 `reloadConfig(...)`。

因此：

- 主类需要最先读取的项目级配置，可放在 `beforeReloadConfig(...)`；
- 模块配置、语言和业务数据适合在 Holder 的 `reloadConfig(...)` 处理；
- 不要把一次性构造器读取当作可重载配置状态；
- 重新加载后应替换旧状态、关闭或取消旧资源，避免累积监听器、任务或缓存；
- 任何配置键、默认值、迁移规则和类型校验都应有明确错误信息。

## `goto` 配置跳转

启用 `enableConfigGotoFlag` 后，框架可根据配置中的 `goto` 读取另一个文件，并设有最大跳转次数以避免循环。使用它前应确认：

- 跳转路径的解析基准；
- 默认配置是否仍保留清楚的入口；
- 跳转链不会循环；
- 部署和重载时目标文件存在且权限正确。

`goto` 用于明确的配置重定向，不应作为隐藏多环境配置或绕开配置迁移的手段。

## 资源保存规则

`BukkitPlugin.saveResource(String)` 会将 JAR 内资源保存到插件数据目录。项目若拥有多个首次启动资源，应在明确的启用阶段以“仅文件不存在才保存”的策略管理，避免每次启动覆盖管理员修改。

推荐把资源职责拆开：

| 类型 | 建议位置 | 首次启动行为 |
| --- | --- | --- |
| 主配置 | `src/main/resources/config.yml` | 由框架默认保存，或在项目显式策略下保存 |
| 数据库配置 | `src/main/resources/database.yml` | 仅数据库启用时保存与加载 |
| 语言资源 | `src/main/resources/<语言文件>` | 由语言模块策略保存/加载 |
| GUI、物品、内容定义 | `src/main/resources/<目录>/` | 按业务版本和迁移策略保存 |
| 版本迁移记录 | 数据目录下的项目专用文件 | 只由明确迁移逻辑读写 |

不要用“每次覆盖资源”解决配置字段更新。需要配置更新器时，先核对目标模块/工具的行为、注释支持和回退策略。

## 数据库能力

启用数据库通常涉及：

1. 主类 Options 开启 `database(true)`；
2. 提供并维护数据库配置资源；
3. 在合适的 `beforeEnable()` 阶段通过 Options 注册项目的数据库实现；
4. 通过框架提供的连接/Holder 生命周期访问数据库；
5. 决定重载时是否重新读取和重连；
6. 在停用流程前停止数据库相关异步工作，框架随后关闭数据库 Holder。

`getConnection()` 仅在数据库 Holder 已启用时可用；未开启数据库选项时会抛出异常。不要把它作为无条件全局连接入口。

数据库实现还必须自行满足：

- 所有连接、语句、结果集按 JDBC 规则关闭；
- 数据库 I/O 不阻塞服务器不允许阻塞的执行路径；
- 连接池、驱动和动态库的加载方式已验证；
- 表前缀、迁移、事务和错误恢复有项目级设计；
- 重载和停用时不会让仍运行的任务使用已关闭连接。

## 经济接口

经济能力通过 Options 声明策略，例如 Vault 或自定义实现。选择后应核验：

- `VaultAPI` 或其它依赖是否保持 `compileOnly`；
- `plugin.yml` 中依赖是硬依赖还是软依赖；
- 缺失经济服务时是否允许回退至无经济实现；
- 自定义经济初始化、错误信息和业务调用是否与策略一致。

不要只因服务器常见安装 Vault 就假设其服务一定可用。

## 动态库、resolver 与类加载器

模板可使用 LibrariesResolver 生成运行时所需库的清单，并在主类构造器中处理服务端 libraries 支持差异。该模式的要素是：

- `base.library(...)` 收集需下载的库；
- `base.doResolveLibraries()` 与 `BuildConstants.RESOLVED_LIBRARIES` 生成可解析清单；
- `plugin.yml` 含对应 libraries 配置；
- 主类在必要时创建 `DefaultLibraryResolver`，读取覆盖配置、下载库并通过框架类加载器添加 URL；
- 库文件落在服务端支持的 `libraries/` 或插件数据目录的 `libraries/`。

这些部分是一个整体。禁用 resolver、加入新动态库或改造启动逻辑时，必须逐项核验构建输出、`plugin.yml`、生成常量和运行期回退路径。

### 依赖覆盖

模板支持 `./.override-libraries.yml` 一类的本地覆盖文件。其用途是让部署者替换已解析库的起始地址/坐标策略；它不应被 Agent 用来掩盖错误依赖坐标或跳过版本验证。

覆盖文件的字段和解析行为以 LibrariesResolver 对应版本资料为准。

## 失败处理

- 动态库失败：报告坐标、仓库、目标路径、网络/哈希状态与受影响功能；不要吞掉 `LinkageError` 后继续假设类可用。
- 配置失败：标明文件、键、期望类型、实际值和安全的修复建议；避免悄悄使用错误默认值损坏数据。
- 数据库失败：停止依赖数据库正确性的功能，避免半启用状态；遵循 Options 的禁用策略。
- 可选依赖失败：仅隔离和禁用相应可选模块，不破坏不依赖它的主功能。

具体符号、配置格式和解析细节必须按当前 PluginBase 与 LibrariesResolver 版本取证。
